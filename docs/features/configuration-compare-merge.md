# Сравнение и объединение конфигураций

Compare-view открывается командой **CDT 41: Сравнить/объединить конфигурацию из файлов...** на узле корня конфигурации. Выбранный корень становится целью и отображается слева; выбранная файловая выгрузка — источником справа. Чтобы перенести изменения в обратную сторону, запустите сравнение от другой целевой конфигурации.

## Что сравнивается

- Метаданные индексируются из XML и сопоставляются по UUID, затем по квалифицированному имени. Конфликты идентичности — например, одинаковое имя при разных UUID — требуют отдельного решения и не разрешаются автоматически.
- BSL-модули сравниваются по процедурам и функциям. Добавленная процедура считается отдельным изменением; сдвиг соседнего кода сам по себе не создаёт конфликт.
- Модули целиком «только слева» или «только справа» отображаются как различия.

## Объединение BSL

Logical merge процедур принимает только построенный и одобренный preview, повторно проверяет guards перед записью, создаёт backup и блокирует сомнительные случаи. Если изменяется существующий блок внутри процедуры, решение остаётся за пользователем.

В интерактивном compare-view можно выбрать исполняемый узел BSL, построить preview, подтвердить его и выполнить merge через общий preflight/executor. Webview отправляет только node ID или preview ID; содержимое файлов и mutation payload остаются в extension host.

## Перенос объектов CF и CFE

Issue #336 добавляет сравнение, выбор, preview, одобрение и применение выбранных объектов для CF↔CFE и CFE↔CFE. Выбор объектов выполняется пакетом в одном preview. В этих направлениях действие является явным upsert: невыбранные или отсутствующие объекты не удаляются автоматически.

Для переноса объектов CF↔CFE и CFE↔CFE поддерживаются корневые типы **Catalog**, **Document**, **Enum** и **CommonModule**. Это ограничение относится только к новым передачам объектов #336; оно не ограничивает существующее поведение CF↔CF или сравнение и объединение BSL. Первоначально поддерживаются только файловые выгрузки Designer форматов 2.17–2.21; для переноса версии обеих сторон должны совпадать. EDT и неизвестные версии отображаются как неподдерживаемые. Если обнаружены признаки CFE, повреждённая или неизвестная CFE-разметка блокирует действие, а сравнение не переключается на общий XML-перенос.

| Направление и объект | Поведение |
| --- | --- |
| Собственный объект | Переносится полный поддерживаемый дескриптор и обычные sidecar-файлы с исходными байтами и UUID. Добавление регистрирует объект в целевом Configuration.xml; замена допустима только при совпадающей идентичности. Для нового собственного объекта CFE имя должно соответствовать NamePrefix. |
| CF → CFE, объект есть в доказанной базе цели | Создаётся adopted shell, связанный с объектом базы; полное тело базового объекта и его модули в shell не копируются. Для уже adopted object допускается только явно поддержанный overlay свойств. |
| CF → CFE, объект не входит в доказанную базу цели | Объект может переноситься как собственный при проверках имени, идентичности и зависимостей. Другая явно указанная база допускает такой перенос; противоречие или повреждение manifest блокирует действие. |
| CFE → CF, adopted object | Требуется совпадение UUID доказанной базы. Переносятся только явно поддержанные свойства с сохранением identity и остальных свойств CF. Любые sidecar-файлы или children вне пустого каркаса делают перенос целого объекта неподдерживаемым. Adopted формы и перехваты BSL нельзя молча отбросить или превратить в обычные модули. |
| CFE → CFE, adopted object | Требуются одна и та же доказанная база, одинаковый anchor и одинаковое назначение CFE. Локальный UUID заимствованного объекта в цели сохраняется. Поддерживаемые BSL-перехваты Before/After/Instead и валидный PropertyState сохраняются при переносе. Перенос между разными назначениями CFE явно неподдерживаем. |

Создание собственного объекта CFE разрешено для назначений AddOn и Customization. Создание собственного объекта для Patch блокируется до подтверждения соответствующей платформенной политики; обновление существующего собственного объекта сохраняет назначение CFE.

Связи CFE с базой берутся из существующего manifest проекта в пределах открытого workspace. Для CF↔CFE сторона CF может считаться базой только если нет другой явной связи и совместимость подтверждена. Для adopted-переноса CFE↔CFE требуется явная общая связь с базой; совпадение имён само по себе её не доказывает. Собственные объекты CFE↔CFE могут переноситься и без такой связи.

Известные корневые ссылки XML — `cfg:` types, typed `MDObjectRef` и `DesignTimeRef` — должны разрешаться в выбранном пакете, цели или привязанной базе. Например, для `Enum.Name.EnumValue.Value` проверяется корневой `Enum.Name`; отдельная проверка вложенных EnumValue не заявлена. Значение того же вида с `xsi:type="xs:string"` считается литералом. Зависимости не копируются автоматически и имена не переименовываются. Динамические BSL-ссылки нельзя доказать статически. Роли и RLS не заявлены как эквивалентно поддержанные.

## Проверка на платформе

Четыре сценария прошли на 1С 8.3.27.1859 через `ibcmd`: borrowed CommonModule CF→CFE прошёл импорт, проверку, применение и повторный экспорт расширения; CFE→CF с adopted Comment и с добавлением собственного CommonModule прошёл импорт, проверку и применение базовой конфигурации с экспортом результата; CFE→CFE с adopted и собственным CommonModule прошёл импорт, проверку, применение и экспорт расширения. Вызов BSL-перехватчиков самим runtime не проверялся; CFE→CFE сценарий подтвердил перенос adopted descriptor и собственного CommonModule.

## Preview, запись и восстановление

Preview показывает для каждого выбранного файлового эффекта относительный путь в цели, создание, замену или удаление и признак разрушительного действия. Если замена sidecar-дерева удаляет оставшиеся в цели файлы, удаление отображается в preview и требует явного подтверждения.

CAS-проверки хэшей защищают целевые файлы и файловые деревья от параллельного изменения. Source/base witnesses проверяются повторно непосредственно перед записью, в том числе после ожидания блокировки; изменение источника блокирует применение. Запись идёт через общий ConfigurationMutationEngine с журналом и восстановлением, а источники остаются read-only. После операции extension host возвращает mutation receipt, а compare-view обновляет состояние. Если запись завершилась, но обновление сравнения не удалось, результат и сведения о backup остаются видимыми, а устаревшие действия блокируются.

## Текущие ограничения

- Структурное объединение XML-метаданных доступно только для явно поддержанных узлов и требует проверки результата.
- Полноценное трёхстороннее объединение и ручное разрешение конфликтов #333, новые snapshots #334 и глубокое слияние #335 не входят в этот сценарий.
- Поддержка ограничена указанными типами, форматами и CFE-сценариями. Неоднозначная идентичность, несовпадение базы, неизвестное назначение и неподдерживаемые зависимости блокируют перенос.
- В режиме переноса CF↔CFE и CFE↔CFE за один preview можно применить выбранный пакет поддерживаемых объектов; отсутствие объекта на одной стороне не трактуется как команда удаления. Это правило не меняет legacy CF↔CF сценарий с существующими операциями удаления файлов и каталогов.
