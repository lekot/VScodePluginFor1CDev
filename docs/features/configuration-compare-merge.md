# Сравнение и объединение конфигураций

Compare-view открывается командой **CDT 41: Сравнить/объединить конфигурацию из файлов...** на узле корня конфигурации. Выбранный корень становится целью и отображается слева; выбранная файловая выгрузка — источником справа. Чтобы перенести изменения в обратную сторону, запустите сравнение от другой целевой конфигурации.

## Что сравнивается

- Метаданные индексируются из XML и сопоставляются по UUID, затем по квалифицированному имени. Конфликты идентичности — например, одинаковое имя при разных UUID — требуют отдельного решения и не разрешаются автоматически.
- BSL-модули сравниваются по процедурам и функциям. Добавленная процедура считается отдельным изменением; сдвиг соседнего кода сам по себе не создаёт конфликт.
- Модули целиком «только слева» или «только справа» отображаются как различия.

## Объединение BSL

Logical merge процедур принимает только построенный и одобренный preview, повторно проверяет guards перед записью, создаёт backup и блокирует сомнительные случаи. Если изменяется существующий блок внутри процедуры, решение остаётся за пользователем.

В интерактивном compare-view можно выбрать исполняемый узел BSL, построить preview, подтвердить его и выполнить merge через общий preflight/executor. Webview отправляет только node ID или preview ID; содержимое файлов и mutation payload остаются в extension host.

## Перенос объектов CF и CFE

Issue #336 добавляет сравнение, выбор, preview, одобрение и применение выбранных объектов для CF↔CFE и CFE↔CFE. Выбор выполняется пакетом в одном preview. В этих направлениях действие является явным upsert: невыбранные или отсутствующие объекты не удаляются автоматически.

Корневой тип определяется общим реестром `METADATA_TYPE_DESCRIPTORS` — сейчас это 46 типов. Реестр включает прикладные объекты (Catalog, Document, Enum, Report, DataProcessor, ChartOfCharacteristicTypes, ChartOfAccounts, ChartOfCalculationTypes, BusinessProcess, Task, ExchangePlan, DocumentJournal, Sequence, FilterCriterion и Constant), четыре регистра (InformationRegister, AccumulationRegister, AccountingRegister и CalculationRegister), а также общие, служебные и интеграционные объекты: ExternalDataSource, SettingsStorage, SessionParameter, ScheduledJob, FunctionalOption, FunctionalOptionsParameter, EventSubscription, CommonModule, CommandGroup, Role, Interface, Style, Subsystem, DocumentNumerator, DefinedType, CommonAttribute, CommonCommand, CommonForm, CommonPicture, CommonTemplate, Language, StyleItem, WebService, HTTPService, IntegrationService, WSReference и XDTOPackage. Реестр задаёт типы, которые можно анализировать и передавать; он сам по себе не означает, что каждый XML-вариант прошёл проверку платформой.

Поддерживаются файловые выгрузки Designer XML форматов 2.17–2.21; версии обеих сторон должны совпадать. EDT и неизвестные версии отображаются как неподдерживаемые. Если обнаружены признаки CFE, повреждённая или неизвестная CFE-разметка блокирует действие, а сравнение не переключается на общий XML-перенос.

| Направление и объект | Поведение |
| --- | --- |
| Собственный объект | Переносятся полный XML-дескриптор, его inline-дети (например, реквизиты и табличные части) и sidecar-дерево с исходными байтами и UUID. Добавление регистрирует объект в целевом Configuration.xml; замена допустима только при совпадающей идентичности. Для нового собственного объекта CFE имя должно соответствовать NamePrefix. Если целевая база известна, совпадение QName с зарегистрированным объектом базы или UUID с любым её собственным объектом блокирует создание и замену; это не считается доказательством для заимствования. При неизвестной базе проверка отсутствия таких объектов не заявляется. |
| CF → CFE, объект есть в доказанной базе цели | Создаётся минимальный adopted shell: `ObjectBelonging=Adopted`, исходные Name/Comment и UUID в `ExtendedConfigurationObject`. `InternalInfo` и GeneratedType имена, категории и UUID копируются из точного дескриптора базы. Для типов с `ChildObjects` создаётся пустой узел; inline-дети, модули и sidecar-дерево базы в расширение не копируются. |
| CF → CFE, объект не входит в доказанную базу цели | Объект может переноситься как собственный при проверках имени, идентичности и зависимостей. Другая явно указанная база допускает такой перенос; противоречие или повреждение manifest блокирует действие. |
| CF → CFE, borrowed properties | В shell из исходного дескриптора копируются имеющиеся CommonModule флаги Global, ClientManagedApplication, Server, ExternalConnection, ClientOrdinaryApplication и ServerCall; у Language — LanguageCode; у InformationRegister — InformationRegisterPeriodicity и WriteMode; у Constant — Type; у CommonForm — FormType. Значения переносятся как XML. Неизвестные обязательные свойства не заполняются догадками. |
| CFE → CF, adopted object | Требуется совпадение UUID доказанной базы. Разрешён только явно поддержанный overlay свойств поверх текущего объекта CF с сохранением identity и остальных свойств CF. Inline-дети, sidecar-файлы, формы или BSL-перехваты нельзя сплющивать в свойства CF; если такой материал есть, перенос блокируется как неподдерживаемый. |
| CFE → CFE, adopted object | Требуются одна и та же доказанная база, одинаковый anchor и одинаковое назначение CFE. Локальный UUID заимствованного объекта в цели сохраняется. Поддерживаемые BSL-перехваты Before/After/Instead и валидный PropertyState сохраняются при переносе. Перенос между разными назначениями CFE явно неподдерживаем. |

Создание собственного объекта CFE разрешено для назначений AddOn и Customization. Создание собственного объекта для Patch блокируется до подтверждения соответствующей платформенной политики; обновление существующего собственного объекта сохраняет назначение CFE.

Связи CFE с базой берутся из существующего manifest проекта в пределах открытого workspace. Для CF↔CFE сторона CF может считаться базой только если нет другой явной связи и совместимость подтверждена. Для adopted-переноса CFE↔CFE требуется явная общая связь с базой; совпадение имён само по себе её не доказывает. Собственные объекты CFE↔CFE могут переноситься и без такой связи, но известная база цели всё равно проверяется на совпадение QName и UUID.

Известные корневые ссылки XML — `cfg:` types, typed `MDObjectRef`, `DesignTimeRef` и прямой `Rights/Object/Name` — проверяются по выбранным объектам, целевой конфигурации и доказанной базе. Например, для `Enum.Name.EnumValue.Value` проверяется корневой `Enum.Name`; отдельная проверка вложенных EnumValue не заявлена. Значение того же вида с `xsi:type="xs:string"` считается литералом. В точных структурах корневых `Properties` также проверяются три прямые ссылки без типа: `AccountingRegister/Properties/ChartOfAccounts` → ChartOfAccounts, `CalculationRegister/Properties/ChartOfCalculationTypes` → ChartOfCalculationTypes и `ChartOfAccounts/Properties/ExtDimensionTypes` → ChartOfCharacteristicTypes (последнее свойство необязательно). Когда такой ссылкой пользуется собственный объект, целиком переносимый в CFE, одной записи в базе недостаточно: зависимый объект должен быть объявлен в CFE или входить в выбранный пакет. Выберите или заимствуйте нужный объект; уже присутствующий adopted-объект цели тоже подходит. Для переноса в CF действует обычная проверка по базе.

Для собственного полного переноса AccumulationRegister, AccountingRegister и CalculationRegister требуется эффективный документ-регистратор с прямой ссылкой в `Document/Properties/RegisterRecords/xr:Item`, где `xsi:type` указывает на `MDObjectRef`. Для InformationRegister это требование включается при `WriteMode=RecorderSubordinate`. Ссылка может быть покрыта выбранным Document, документом целевой конфигурации или документом доказанной базы; у adopted Document список регистраторов наследуется из базы. Вложенные `Item`, текстовые совпадения и значения с другим типом не считаются регистраторами; ошибки структуры блокируют перенос. Зависимости не копируются автоматически и имена не переименовываются. Динамические BSL-ссылки нельзя доказать статически; структурная проверка ссылки в `Rights.xml` не доказывает фактический эффект прав или RLS в платформе.

## Проверка на платформе

В production-flow на 1С 8.3.27 через `ibcmd` проверены CF→CFE и CFE→CFE для четырёх типов регистров: AccumulationRegister, AccountingRegister, CalculationRegister и InformationRegister; отдельно проверен перенос всех четырёх собственных регистров вместе с Document-регистратором в обоих направлениях CF↔CFE. В этих сценариях CFE содержит два adopted shell плана счетов и видов расчёта, а сравнение, запись, `import`, `check`, `apply` и повторный `export` завершились успешно. В проверке CF→CFE планы были объявлены в цели до сравнения; через preview переносились четыре регистра и Document. Также ранее проверялся borrowed Catalog shell: общий каркас, исходный `InternalInfo` с неизменёнными GeneratedType и пустой `ChildObjects` прошли импорт, проверку, применение и повторный экспорт. Это проверки конкретных сценариев, а не платформенная приёмка всех 46 типов. Структурный аудит исходных дескрипторов доступных 44 типов также не является импортом или проверкой каждого типа платформой.

## Preview, запись и восстановление

Preview показывает для каждого выбранного файлового эффекта относительный путь в цели, создание, замену или удаление и признак разрушительного действия. Если замена sidecar-дерева удаляет оставшиеся в цели файлы, удаление отображается в preview и требует явного подтверждения.

CAS-проверки хэшей защищают целевые файлы и файловые деревья от параллельного изменения. Source/base witnesses проверяются повторно непосредственно перед записью, в том числе после ожидания блокировки; изменение источника блокирует применение. Запись идёт через общий ConfigurationMutationEngine с журналом и восстановлением, а источники остаются read-only. После операции extension host возвращает mutation receipt, а compare-view обновляет состояние. Если запись завершилась, но обновление сравнения не удалось, результат и сведения о backup остаются видимыми, а устаревшие действия блокируются.

## Текущие ограничения

- Структурное объединение XML-метаданных доступно только для явно поддержанных узлов и требует проверки результата.
- Полноценное трёхстороннее объединение и ручное разрешение конфликтов #333, новые snapshots #334 и глубокое слияние #335 — отдельные задачи и не входят в #336.
- Типы и Designer XML версии задаются реестром и указанными форматами; неоднозначная идентичность, несовпадение базы, неизвестное назначение и неподдерживаемые зависимости блокируют перенос.
- В режиме переноса CF↔CFE и CFE↔CFE за один preview можно применить выбранный пакет поддерживаемых объектов; отсутствие объекта на одной стороне не трактуется как команда удаления. Это правило не меняет legacy CF↔CF сценарий с существующими операциями удаления файлов и каталогов.
