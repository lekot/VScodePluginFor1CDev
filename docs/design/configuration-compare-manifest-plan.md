# Manifest-first сравнение конфигураций

## Цель и ограничения

Целевое сравнение должно быстро показывать наличие объектов и модулей, не разбирая глубоко содержимое, которое заведомо совпадает или не участвует в выбранном действии. Пользователь должен видеть модули BSL как основные строки и открывать детали конкретного модуля отдельно. В целевой модели обе стороны обнаруживаются симметрично, а направление переноса и допустимые действия применяются после сопоставления. Одобренный сейчас второй коммит уже этой цели: он симметризует только discovery CF metadata.

Профиль на одном build завершил сравнение `empty_conf` → `FormatSamples/uh` за 249,020 мс и достиг RSS 3,068,862,464 B; обратное направление завершилось за 15,973 мс. Это по одному запуску без сброса OS-кэша и без p95. На образце `uh` обнаружено 28,795 BSL-файлов против 4 в пустой конфигурации; пересечение BSL module IDs равно нулю. Предыдущая направленная выборка в 28,791 прочитанных модулей была ограниченной областью измерения, а не полным инвентарём обеих конфигураций. Эти цифры показывают потенциальную ценность раннего presence-результата и пропуска не нуждающегося в анализе BSL, но не позволяют обещать конкретное ускорение.

Сохраняются текущие правила UUID и identity matching, политики допустимых CF/CFE операций, candidate IDs, preview/approve/execute, file witnesses, CAS-проверки, backup и восстановление. Новый симметричный discovery показывает presence обеих сторон независимо от стратегии, но сам по себе не разрешает запись или удаление. Текущая CF-стратегия `right` скрывает часть противоположных unmatched-объектов; новая модель показывает их, сохраняя существующую политику разрешённых CF-действий. CFE уже сопоставляется симметрично, игнорирует стратегию и не трактует отсутствие как удаление. Автоматическая замена UUID и семантическое слияние EDT не входят в план.

## Варианты дизайна и решение

| Вариант | Изменение | Компромисс |
| --- | --- | --- |
| Минимальный | Пропускать разбор неподдерживаемых или unmatched BSL после текущего направленного inventory. | Малый риск и быстрый первый шаг, но не даёт симметричного discovery, manifest-view или инвентаря для смены направления. |
| Manifest-first, выбран | Сканировать обе стороны, сопоставить manifest по существующим type/name/UUID правилам, отделить presence и directional capabilities, сравнивать hashes пересечений, глубоко анализировать только изменённые пары. Для BSL показывать модульный список и запрашивать детали модуля отдельно. | Требует промежуточного контракта manifest и двухфазной модели данных; сохраняет существующие анализаторы и безопасную запись. Реализация разбивается на совместимые этапы. |
| Переписать engine и snapshots | Заменить инвентарь, сравнение и snapshot lifecycle единым новым движком. | Потенциально проще финальная архитектура, но высокая площадь изменения identity, witnesses, cancellation и merge guards; отвергнут для этой итерации. |

Выбран manifest-first вариант. Первый коммит ограничен селективным BSL-анализом. Второй одобренный коммит симметризует CF metadata discovery, но не расширяет инвентарь файлов или descriptors. Модульный BSL экран, селективная гидратация остальных данных и пропуск равных файлов остаются направлениями для отдельных design/spec review; этот документ не утверждает, что полный manifest, симметричный inventory или performance acceptance уже реализованы.

## Контракты и поток данных

1. Целевой dataflow начинает с независимого discovery обоих корней. Для CF metadata фиксируются сторона, тип, имя и UUID по существующим indexer правилам. BSL manifest и полное сравнение artifact paths относятся к отдельным будущим этапам. В коммите 2 симметрично индексируется только CF metadata; scope inventory и descriptor files остаётся текущим.
2. Сопоставление использует существующие правила идентичности и их приоритеты. Оно сохраняет неоднозначность и конфликты как отдельные read-only результаты; дубликаты module ID не сливаются в одну actionable строку. Новые правила UUID не выводятся из имени, пути или интерфейсной подписи.
3. Unmatched metadata и модули классифицируются как присутствующие только на одной стороне. Для BSL сохраняются существующие file-copy/delete узлы и canonical IDs. Manifest не создаёт второй узел или candidate для того же файла.
4. Для каждой пары matched artifacts сравниваются имеющиеся content hashes. Равные хеши могут пропустить глубокий adapter analysis; разные хеши направляются в уже существующий semantic XML или BSL analyzer. Само пропускание equal-pair analysis вводится отдельным последующим этапом после проверки всех зависимых consumers.
5. Направление переноса и capabilities вычисляются из manifest с учётом существующих CF/CFE правил. Симметричная видимость не меняет список поддержанных действий и не преобразует unmatched в delete без существующего доказательства и guard.
6. Основной BSL экран показывает по одной строке на однозначную canonical module identity: имя/тип, присутствие и статус содержимого. Неоднозначные module IDs остаются раздельными read-only строками. Панель деталей показывает сравнение routines только для выбранного модуля. Незагруженная или отложенная деталь не маркируется равной. Поиск, фильтр и выбор не создают executable IDs; операции остаются привязаны к canonical candidate IDs и существующим host guards.
7. Перестановка сторон строит ту же модель с зеркальными сторонами и заново применёнными directional capabilities. Ошибки, отмена, диагностики, порядок результатов и hash snapshots должны оставаться воспроизводимыми.

## Первый коммит: отложить анализ ненужных BSL-модулей

Этот этап сохраняет полное чтение, hash и module identity discovery, но не запускает parser для supported module paths, которым не нужны routine details в текущем сравнении. Равные matched пары намеренно остаются полностью анализируемыми в этом коммите; их hash-skip появится после manifest integration.

- **Файлы:** `src/compareMerge/bsl/bslModuleIndexer.ts`, `src/compareMerge/bsl/bslInventoryCollection.ts`, `src/compareMerge/bsl/bslRoutineDiff.ts`, `src/compareMerge/configurationCompareService.ts`; целевые тесты BSL indexer/collector/routine diff и `configurationCompareService.test.ts`.
- **Изменения:** коллектор продолжает читать и хешировать все inventory paths в прежнем порядке, сохраняет прежние diagnostics unsupported identities и cancellation/drain семантику. Он получает набор путей, для которых нужен routine analysis. Для supported identity вне набора создаётся identity-only entry, parser не вызывается. Сервис формирует наборы из `retention.leftPaths` и `retention.rightPaths`: он включает обе стороны paired module IDs, дубликаты консервативно остаются анализируемыми, а правый FormModule для matched Form/CommonForm включается для сценария отсутствующего target FormModule. Это сохраняет связанный handler proof. Неизвестная или неподдержанная identity не становится молча deferred вместо существующей диагностики.
- **Контракты:** `BslModuleIndexEntry.analysisState?: 'complete' | 'deferred'`; отсутствие поля означает `complete` и сохраняет совместимость ранее создаваемых записей. В `collectBslInventorySources(input)` добавляется необязательное `analysisPaths?: ReadonlySet<string>`; его отсутствие означает прежнее поведение «анализировать все». Значения набора используют те же path keys, что и inventory collector. Для supported entries вне набора возвращаются identity, пустые `routines` и `diagnostics`, состояние `deferred`; текст файла всё равно читается для существующего полного hash-контракта, но parser не вызывается. В `BslModuleDiagnosticCode` добавляется `BSL_MODULE_ANALYSIS_REQUIRED` с русским сообщением. Если `diffBslModules` получает deferred entry, он возвращает блокирующую диагностику для каждой такой стороны с `sourceId`, side, `filePath` и `moduleId` из identity, пустой список routines и `canAutoMatch: false`; deferred никогда не превращается в ложное «без изменений».
- **Проверки:** отсутствие `analysisPaths` эквивалентно старому полному анализу; unmatched supported module с содержимым, которое дало бы parse diagnostic, остаётся в manifest как deferred без parse diagnostic; paired modules на обеих сторонах и явный linked right FormModule остаются complete; unsupported identities сохраняют диагностики; общий hash/order/read-count и cancellation сохраняются; deferred routine diff блокируется; существующие missing-target-form и linked-handler интеграции проходят без изменения candidate IDs.

## Одобренный следующий коммит

### Коммит 2: симметрично обнаруживать CF metadata независимо от стратегии

- **Файлы:** новый `src/compareMerge/configurationCompareManifest.ts`; `src/compareMerge/configurationCompareService.ts`; `test/suite/compareMerge/configurationCompareService.test.ts`. Переиспользуются без изменений `src/compareMerge/metadata/metadataIndexer.ts`, `src/compareMerge/metadata/metadataMatcher.ts` и `src/compareMerge/inventory/configurationInventory.ts`.
- **Изменения:** новый metadata-only discovery индексирует обе CF стороны через существующий `indexMetadataFolder`, дожидается обеих сторон через существующий `awaitAllSettled` и запускает существующий matcher один раз. Оно не принимает strategy и не расширяет descriptor/inventory scope. Service берёт обе metadata lists и единый match result, удаляет прежний `indexMetadataForStrategy` и целевые counterpart helpers/constants/imports только если они больше нигде не используются. Compare view показывает metadata-only presence с обеих сторон: при стратегии `right` unmatched слева остаётся видимым, но не получает нового executable действия. Действующие candidate operations, scoped inventory, copy/delete policy и guards сохраняются. Не добавляются synthetic unmatched-object fallback и новый delete proof. CFE-маршрут и его proof не меняются; глобальный default `full` не вводится.
- **Контракт:** `discoverConfigurationCompareManifest(input: { left: { sourceId: string; rootPath: string }; right: { sourceId: string; rootPath: string }; metadataReadConcurrency: number; directoryReadConcurrency: number; cancellation?: CompareCancellationToken }): Promise<{ leftMetadata: MetadataIdentity[]; rightMetadata: MetadataIdentity[]; metadata: MatchResult }>`.
- **Проверки:** перестановка root сторон зеркально меняет `leftMetadata`/`rightMetadata`, а MatchResult сохраняет существующие правила; результат discovery одинаков при текущих strategy settings, поскольку API не принимает strategy. При default `right` unmatched left metadata видна и остаётся non-executable без новых candidates; противоположная unmatched сторона также видна, а её операции определяются только прежней policy. Дубли UUID и конфликты type/name сохраняются. Тесты старого directional omission обновляются, а существующие preview, copy/delete и CFE proof tests остаются зелёными.

## Дальнейшие направления требуют отдельного Spec Review

Ниже — последовательность исследования после коммита 2, а не утверждение готового контракта. Перед реализацией необходимо согласовать descriptor scope, synthetic unmatched behavior, delete proof/candidate policy и CFE route; текущий коммит их не меняет.

### Оставшееся требование: модульное BSL представление и детали по запросу

- **Файлы:** `src/compareMerge/compareTreeTypes.ts`, `src/compareMerge/projection/compareTreeProjection.ts`, `src/compareMerge/projection/compareDisplayTree.ts`, `src/compareMerge/configCompareProvider.ts`, `src/compareMerge/configCompareMessages.ts`, `src/compareMerge/configCompareWebview.html`; provider/display/browser suites.
- **Изменения:** верхний уровень BSL показывает модули, выбранный модуль загружает либо раскрывает routine-level детали. Запросы деталей несут session generation и canonical module ID; устаревший ответ игнорируется. Результат деталей read-only до готового canonical compare result; preview и execution используют существующую selection/materialization цепочку.
- **Требования к будущему контракту:** detail request/response должен быть привязан к `generation + moduleId`, различать phase/state (`loading`, `complete`, `deferred`, `error`, `cancelled`) и сохранять canonical node/candidate IDs. `deferred`/`loading` не отображаются как equal и не допускают write actions. Один модуль не требует разборки всех routine trees. Сам protocol и ownership деталей требуют отдельного Design/Spec Review.

### Оставшееся требование: пропускать глубокий diff равных файлов и измерять остаточную стоимость

- **Файлы:** `src/compareMerge/configurationCompareManifest.ts`, `src/compareMerge/configurationCompareService.ts`, `src/compareMerge/bsl/bslInventoryCollection.ts`, adapter routing and snapshot/hash collection, performance harnesses и targeted equivalence suites.
- **Изменения:** при точном совпадении hashes парный файл не отправляется в глубокий parser; изменённые пары анализируются существующими adapters. Отдельно измерить, можно ли ограничить чтение и hashing без потери witness/CAS-контракта; до доказательства оставить чтение всех source paths. Снимать обе ориентации, first/pending/final projections, время фаз, bytes/read counts, peak RSS/heap, delay cancellation и equivalence.
- **Требования к будущему контракту:** отсутствие анализа допустимо только при доказанном точном hash equality в рамках одного snapshot; пропущенная пара должна иметь состояние `equal-by-hash`, а не пустое/отложенное сравнение. Любое действие перед записью проходит текущие guards и witness/CAS-проверки, включая предусмотренные ими повторные чтения. Оптимизация не подменяет captured snapshot и не меняет его revision. Точные точки hash-skip и безопасного сокращения чтения требуют отдельного Design/Spec Review.

## Приёмка и границы

Первый коммит принят только если тесты подтверждают отсутствие parser-вызова для deferred paths, полноту hash/identity/diagnostics, неизменность paired и linked Form анализов, fail-closed deferred diff, отмену и эквивалентность прежнего поведения при `analysisPaths` отсутствующем. Следующие этапы не объединяются с ним: symmetric manifest, directional policy и UI требуют собственных RED/GREEN контрактов.

Полная готовность не объявляется по одному завершённому большому прогону. Нужны повторные серии и обе ориентации на одинаковых данных, меньшие и большие пары с одинаковым и различным содержимым, native VS Code проверка и полная матрица CF↔CF/CF↔CFE/CFE↔CFE. До подтверждения этих сценариев статус производительности остаётся **PARTIAL**.
