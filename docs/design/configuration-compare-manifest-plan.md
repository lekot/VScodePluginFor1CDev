# Manifest-first сравнение конфигураций

## Цель и ограничения

Целевое сравнение показывает наличие объектов и модулей и сохраняет глубокий анализ каждой сопоставленной пары BSL до состояния «готово». Module-only представление BSL остаётся будущим направлением: текущий compare-view показывает routine rows, а детали пар уже проанализированы. Несопоставленный BSL-модуль переносится целиком в рамках существующего file-copy/delete узла, без routine-level diff. В целевой модели обе стороны обнаруживаются симметрично, а направление переноса и допустимые действия применяются после сопоставления. Одобренный второй коммит симметризует только discovery CF metadata.

Профиль на одном build завершил сравнение `empty_conf` → `FormatSamples/uh` за 249,020 мс и достиг RSS 3,068,862,464 B; обратное направление завершилось за 15,973 мс. Это по одному запуску без сброса OS-кэша и без p95. На образце `uh` обнаружено 28,795 BSL-файлов против 4 в пустой конфигурации; пересечение BSL module IDs равно нулю. Предыдущая направленная выборка в 28,791 прочитанных модулей была ограниченной областью измерения, а не полным инвентарём обеих конфигураций. Эти данные не измеряют цену полного анализа сопоставленных BSL-модулей и не позволяют обещать ускорение.

Сохраняются текущие правила UUID и identity matching, политики допустимых CF/CFE операций, candidate IDs, preview/approve/execute, file witnesses, CAS-проверки, backup и восстановление. Новый симметричный discovery показывает presence обеих сторон независимо от стратегии, но сам по себе не разрешает запись или удаление. Текущая CF-стратегия `right` скрывает часть противоположных unmatched-объектов; новая модель показывает их, сохраняя существующую политику разрешённых CF-действий. CFE уже сопоставляется симметрично, игнорирует стратегию и не трактует отсутствие как удаление. Автоматическая замена UUID и семантическое слияние EDT не входят в план.

## Варианты дизайна и решение

| Вариант | Изменение | Компромисс |
| --- | --- | --- |
| Минимальный | Пропускать разбор неподдерживаемых или unmatched BSL после текущего направленного inventory. | Малый риск и быстрый первый шаг, но не даёт симметричного discovery, manifest-view или инвентаря для смены направления. |
| Manifest-first, выбран | Сканировать обе стороны, сопоставить manifest по существующим type/name/UUID правилам и отделить presence от directional capabilities. Все сопоставленные пары BSL глубоко анализировать до готовности сравнения; одиночные BSL-модули оставлять whole-file операциями. | Требует промежуточного контракта manifest; сохраняет существующие анализаторы и безопасную запись. Равный hash не заменяет routine analysis для сопоставленной BSL-пары. |
| Переписать engine и snapshots | Заменить инвентарь, сравнение и snapshot lifecycle единым новым движком. | Потенциально проще финальная архитектура, но высокая площадь изменения identity, witnesses, cancellation и merge guards; отвергнут для этой итерации. |

Выбран manifest-first вариант. Селективный routine analysis допускается только для несопоставленных BSL-модулей, которые остаются whole-file операциями; каждая сопоставленная BSL-пара анализируется полностью до готовности сравнения. Второй одобренный коммит симметризует CF metadata discovery, но не расширяет инвентарь файлов или descriptors. Пропуск анализа равных BSL-пар не входит в принятое направление и не может служить основанием для выбора всех доступных изменений.

## Контракты и поток данных

1. Целевой dataflow начинает с независимого discovery обоих корней. Для CF metadata фиксируются сторона, тип, имя и UUID по существующим indexer правилам. BSL manifest и полное сравнение artifact paths относятся к отдельным будущим этапам. В коммите 2 симметрично индексируется только CF metadata; scope inventory и descriptor files остаётся текущим.
2. Сопоставление использует существующие правила идентичности и их приоритеты. Оно сохраняет неоднозначность и конфликты как отдельные read-only результаты; дубликаты module ID не сливаются в одну actionable строку. Новые правила UUID не выводятся из имени, пути или интерфейсной подписи.
3. Unmatched metadata и модули классифицируются как присутствующие только на одной стороне. Для BSL сохраняются существующие whole-file copy/delete узлы и canonical IDs. Manifest не создаёт второй узел или candidate для того же файла.
4. Сопоставленные пары BSL всегда проходят существующий глубокий анализ до готовности, даже если их hashes равны. Для остальных artifact classes hash-based оптимизация может рассматриваться отдельно, только после проверки зависимых consumers и без изменения witness/CAS guards.
5. Направление переноса и capabilities вычисляются из manifest с учётом существующих CF/CFE правил. Симметричная видимость не меняет список поддержанных действий и не преобразует unmatched в delete без существующего доказательства и guard.
6. Основной BSL экран показывает по одной строке на однозначную canonical module identity: имя/тип, присутствие и статус содержимого. Все routine comparisons для сопоставленных module IDs готовы до публикации состояния `ready`; интерфейс может отложить только рендеринг деталей. Несопоставленные модули используют whole-file operations и не изображаются как routine-level равенство. Поиск, фильтр и выбор не создают executable IDs; операции остаются привязаны к canonical candidate IDs и существующим host guards.
7. Перестановка сторон строит ту же модель с зеркальными сторонами и заново применёнными directional capabilities. Ошибки, отмена, диагностики, порядок результатов и hash snapshots должны оставаться воспроизводимыми.

## Первый коммит: отложить анализ ненужных BSL-модулей

Этот этап сохраняет полное чтение, hash и module identity discovery, не запуская parser для supported unmatched module paths, которые остаются whole-file операциями. Все стороны каждой paired module identity глубоко анализируются при начальной сборке; равные пары не пропускаются по hash.

- **Файлы:** `src/compareMerge/bsl/bslModuleIndexer.ts`, `src/compareMerge/bsl/bslInventoryCollection.ts`, `src/compareMerge/bsl/bslRoutineDiff.ts`, `src/compareMerge/configurationCompareService.ts`; целевые тесты BSL indexer/collector/routine diff и `configurationCompareService.test.ts`.
- **Изменения:** коллектор продолжает читать и хешировать все inventory paths в прежнем порядке, сохраняет прежние diagnostics unsupported identities и cancellation/drain семантику. Он получает набор путей, для которых нужен routine analysis. Для supported unmatched identity вне набора создаётся identity-only entry, parser не вызывается; paired module IDs всегда включаются с обеих сторон. Правый `FormModule` для matched Form/CommonForm остаётся отдельным compatibility path для существующего доказательства обработчика при отсутствующем target FormModule. Эта узкая ветка не доказывает поддержку всех форм и linked-package сочетаний; их контракт требует отдельного design review.
- **Контракты:** `BslModuleIndexEntry.analysisState?: 'complete' | 'deferred'`; отсутствие поля означает `complete` и сохраняет совместимость ранее создаваемых записей. В `collectBslInventorySources(input)` добавляется необязательное `analysisPaths?: ReadonlySet<string>`; его отсутствие означает прежнее поведение «анализировать все». Значения набора используют те же path keys, что и inventory collector. Для supported entries вне набора возвращаются identity, пустые `routines` и `diagnostics`, состояние `deferred`; текст файла всё равно читается для существующего полного hash-контракта, но parser не вызывается. В `BslModuleDiagnosticCode` добавляется `BSL_MODULE_ANALYSIS_REQUIRED` с русским сообщением. Если `diffBslModules` получает deferred entry, он возвращает блокирующую диагностику для каждой такой стороны с `sourceId`, side, `filePath` и `moduleId` из identity, пустой список routines и `canAutoMatch: false`; deferred никогда не превращается в ложное «без изменений».
- **Проверки:** отсутствие `analysisPaths` эквивалентно старому полному анализу; unmatched supported module с содержимым, которое дало бы parse diagnostic, остаётся whole-file узлом без routine parse; все paired modules анализируются на обеих сторонах до состояния `ready`; явный linked right FormModule сохраняет существующий missing-target proof как узкую совместимость; unsupported identities сохраняют диагностики; общий hash/order/read-count и cancellation сохраняются. Новые сценарии форм сверх этой узкой проверки требуют отдельной приёмки.

## Одобренный следующий коммит

### Коммит 2: симметрично обнаруживать CF metadata независимо от стратегии

- **Файлы:** новый `src/compareMerge/configurationCompareManifest.ts`; `src/compareMerge/configurationCompareService.ts`; `test/suite/compareMerge/configurationCompareService.test.ts`. Переиспользуются без изменений `src/compareMerge/metadata/metadataIndexer.ts`, `src/compareMerge/metadata/metadataMatcher.ts` и `src/compareMerge/inventory/configurationInventory.ts`.
- **Изменения:** новый metadata-only discovery индексирует обе CF стороны через существующий `indexMetadataFolder`, дожидается обеих сторон через существующий `awaitAllSettled` и запускает существующий matcher один раз. Оно не принимает strategy и не расширяет descriptor/inventory scope. Service берёт обе metadata lists и единый match result, удаляет прежний `indexMetadataForStrategy` и целевые counterpart helpers/constants/imports только если они больше нигде не используются. Compare view показывает metadata-only presence с обеих сторон: при стратегии `right` unmatched слева остаётся видимым, но не получает нового executable действия. Действующие candidate operations, scoped inventory, copy/delete policy и guards сохраняются. Не добавляются synthetic unmatched-object fallback и новый delete proof. CFE-маршрут и его proof не меняются; глобальный default `full` не вводится.
- **Контракт:** `discoverConfigurationCompareManifest(input: { left: { sourceId: string; rootPath: string; allowMissingRoot?: boolean }; right: { sourceId: string; rootPath: string; allowMissingRoot?: boolean }; metadataReadConcurrency: number; directoryReadConcurrency: number; cancellation?: CompareCancellationToken }): Promise<{ leftMetadata: MetadataIdentity[]; rightMetadata: MetadataIdentity[]; metadata: MatchResult }>`. `allowMissingRoot` по умолчанию `false`; service устанавливает его только для target `left`, не для incoming `right`. Обёртка discovery возвращает пустой список metadata только при явном разрешении и `ENOENT`, если `error.path` после `path.resolve` точно равен запрошенному `rootPath`. Пропуск вложенного файла/каталога, ошибка без `path`, иной путь, `EACCES` и остальные ошибки отклоняются как ошибки discovery. Обе задачи индексации запускаются и дожидаются через `awaitAllSettled`, включая случай ошибки одной стороны.
- **Проверки:** перестановка root сторон зеркально меняет `leftMetadata`/`rightMetadata`, а MatchResult сохраняет существующие правила; результат discovery одинаков при текущих strategy settings, поскольку API не принимает strategy. При default `right` unmatched left metadata видна и остаётся non-executable без новых candidates; противоположная unmatched сторона также видна, а её операции определяются только прежней policy. Дубли UUID и конфликты type/name сохраняются. Отсутствующий target left root при явном разрешении даёт пустую левую metadata list и сохраняет legacy-сценарий; отсутствующий incoming right root всегда отклоняется и не превращается в delete. Ошибки вложенных путей и доступа не скрываются. Тесты старого directional omission обновляются, а существующие preview, copy/delete и CFE proof tests остаются зелёными.

## Одобренный UI-коммит: пакетный выбор без неявного удаления

### Варианты и решение

| Вариант | Изменение | Компромисс |
| --- | --- | --- |
| Переиспользовать список executable IDs для пакетного выбора | Кнопка выбирает каждый executable ID, включая узлы удаления. | Не требует отдельного DTO, но массовое действие неожиданно добавляет удаления и destructive replacement в обычный выбор. |
| Переключить глобальную политику удаления | Изменить классификацию или исполняемость удалений для всех сценариев выбора. | Меняет смысл явного удаления и может ломать существующие операции и preview. |
| Разделить выбор слияния и выбор удаления, выбран | Передать canonical deletion candidates отдельно; обычный пакетный выбор исключает их, а отдельное действие явно добавляет/снимает их с selection. | Добавляет два поля DTO и явное действие в интерфейсе, сохраняя canonical IDs и существующий host-путь выполнения. |

Выбран вариант с отдельным bulk-selection набором и явным delete intent. Пакетный выбор видимых изменений не добавляет новые удаления, но может сохранить уже явно выбранные удаления. Действие выбора удаления только меняет selection; preview, approve, подтверждение разрушительных эффектов и execute остаются обязательными. Кнопка очистки снимает любой выбор.

### План реализации

- **Коммит:** безопасное BSL-слияние, явные logical conflicts и пакетный выбор в compare-view.
- **Файлы:** `src/compareMerge/configurationCompareService.ts`, `src/compareMerge/projection/compareTreeProjection.ts`, `src/compareMerge/configCompareTreePayload.ts`, `src/compareMerge/configCompareProvider.ts`, `src/compareMerge/configCompareMessages.ts`, `src/compareMerge/configCompareWebview.html`, `test/suite/compareMerge/configurationCompareService.test.ts`, `test/suite/compareMerge/compareTreeProjection.test.ts`, `test/suite/compareMerge/configCompareProvider.test.ts`, `test/suite/compareMerge/configCompareWebview.runtime.test.ts`, этот документ и `docs/features/configuration-compare-merge.md`.
- **Изменения:** service вычисляет diff ровно один раз на каждую unambiguous paired BSL identity и строит executable factories только для безопасных routine merges. Рутинные конфликты, требующие ручного merge, становятся отдельными blocking nodes; identity/module guards и diagnostics имеют приоритет, а здоровые соседние процедуры остаются выбираемыми. Unmatched BSL остаётся whole-file операцией. Provider обходит canonical tree для списка delete candidates и числа уникальных blocking conflicts. В webview checkbox строки и родителя с Space выбирают merge candidates; «Выбрать видимое» исключает delete candidates. Для удаления выводится отдельное русское действие выбора/снятия, которое не исполняет операцию. При blocking conflicts показывается заметный banner. Все preview, destructive confirmation и host guards сохраняются. Provider/runtime и service/projection тесты фиксируют поведение до реализации.
- **Контракты:** `BslRoutineDiffProjectionInput` получает `blockedRoutineReasons?: ReadonlyMap<string, string>`, где ключ — canonical routine node ID, значение — причина ручного merge. Карта применяется только к изменённой процедуре без blocking module/routine diagnostics, при точной однозначной paired identity и не ambiguous target; identity/module guards остаются старше logical-conflict результата. `ConfigCompareWebviewPayloadDto` получает совместимые optional поля `deletionNodeIds?: string[]` и `unresolvedConflictCount?: number`; provider всегда заполняет их обходом canonical tree. Delete candidate — executable canonical node со `status === 'leftOnly'` и (`destructive === true` или `kind === 'bslRoutine'`) (удалённые BSL routine узлы пока не имеют `destructive`). Узлы `changed` с destructive file replacement не становятся удалением только из-за `destructive === true`. Conflict count — количество уникальных canonical nodes с `conflict.blocking`. При legacy DTO без `deletionNodeIds` UI выводит deletion IDs из display tree и текущего executable set; если `unresolvedConflictCount` отсутствует, счётчик вычисляется по уникальным display nodes с `conflict.blocking`. Selection продолжает передаваться существующими `selectionChanged` и `createPreview` сообщениями с canonical node IDs; новых host команд нет. Bulk action не вводит deletion IDs, которых не было в явном delete selection; clear selection очищает всё. Любой blocking conflict показывает общий accessible label «Конфликт», включая BSL-узлы.
- **Приёмка:** все paired BSL пары, включая равные по hash, глубоко анализируются до `ready`; diff каждой pair вычисляется один раз. Парные изменённые процедуры, которые нельзя безопасно объединить, блокируются с конкретной причиной; несовпадение identity или module diagnostics сохраняют приоритет, независимые здоровые соседи выбираемы. Provider всегда передаёт точные delete IDs и distinct blocking conflict count; runtime проверяет исключение удаления из пакетного выбора, explicit delete без немедленного execute и видимый конфликтный счётчик/banner. Checkbox строки/родителя работают мышью и Space. В full view при target `Catalog` со значением `Rekv1` и incoming `Rekv2` выбор всех поддерживаемых видимых изменений и выполнение preview оставляют target-only `Рекв1` и добавляют incoming `Рекв2` в resulting XML. Ранее выбранные удаления сохраняются, новые не добавляются; очистка снимает всё. Existing preview, approve, destructive confirmation и execute остаются привязаны к прежнему selection/guards. Несопоставленный `FormModule` и другие новые linked Form proof-сценарии не считаются принятыми этой проверкой.

## Дальнейшие направления требуют отдельного Spec Review

Одобренный UI-коммит выше не меняет descriptor scope, synthetic unmatched behavior, delete proof/candidate policy или CFE route. Любая будущая работа с этими границами требует отдельного design review.

### Hash-based оптимизация других artifact classes

- **Файлы:** manifest/service, adapter routing, snapshot/hash collection, performance harnesses и targeted equivalence suites.
- **Изменения:** измерить, можно ли сокращать анализ для других artifact classes без потери witness/CAS-контракта; до доказательства оставить чтение source paths. Снимать обе ориентации, first/pending/final projections, время фаз, bytes/read counts, peak RSS/heap, delay cancellation и equivalence.
- **Контракт:** ни одна сопоставленная BSL-пара не пропускает глубокий анализ по hash, включая пары с равными hashes. Любая оптимизация других artifact classes должна сохранять полный captured snapshot, его revision и повторные guards/witness проверки. Точные границы требуют отдельного Design/Spec Review.

## Приёмка и границы

Селективный BSL-анализ принят только если тесты подтверждают полноту hash/identity/diagnostics, глубокий анализ обеих сторон каждой paired module identity до готовности, whole-file операции для unmatched modules, fail-closed routine diff для deferred entries, отмену и эквивалентность прежнего поведения при `analysisPaths` отсутствующем. Исключение для правого linked `FormModule` сохраняет только уже существующий missing-target-handler proof и не является приёмкой всех Form/linked-package сценариев. Symmetric manifest, directional policy и UI проходят отдельные RED/GREEN контракты.

Полная готовность не объявляется по одному завершённому большому прогону. Нужны повторные серии и обе ориентации на одинаковых данных, меньшие и большие пары с одинаковым и различным содержимым, native VS Code проверка и полная матрица CF↔CF/CF↔CFE/CFE↔CFE. До подтверждения этих сценариев статус производительности остаётся **PARTIAL**.

## Потоковые снимки для проверки хэшей

### Варианты и решение

| Вариант | Изменение | Компромисс |
| --- | --- | --- |
| Минимальный | Хешировать файлы потоком, оставив обход директорий последовательным. | Ограничивает память размером блока, но сохраняет ожидание каждого файла перед следующим. |
| Ограниченный параллелизм, выбран | Не удерживать содержимое в hash-only snapshots и читать соседние обычные файлы пакетами максимум по два; обход каталогов остаётся последовательным. | Ограничивает память и время ожидания I/O без неограниченного fan-out; требует drain и упорядоченной обработки ошибок. |
| Межфазный кэш | Повторно использовать результаты снимков между стадиями сравнения, descriptor-ами и BSL. | Может убрать повторное чтение, но меняет границы source-read, witness/CAS и контракты текста/raw hash; отложен для отдельного исследования. |

Выбран ограниченный параллелизм. Срез затрагивает только захват merge snapshots. `pairedBSL` по-прежнему всегда проходит полный анализ; hash snapshots не становятся причиной пропуска чтения исходников, lazy witness или CAS-проверок.

### План реализации

- **Коммит:** потоковые hash-only merge snapshots с ограниченной параллельностью соседних файлов.
- **Файлы:** `src/compareMerge/merge/mergeSnapshot.ts`, `test/suite/compareMerge/capturedFileWrite.test.ts`, `test/suite/compareMerge/extensionCompareValidation.test.ts`, этот документ.
- **Изменения:** режим `retainContent: false` считает SHA-256 из блоков постоянного размера, при необходимости пробует XML-корень по первым 64 КиБ и закрывает каждый файловый handle при успехе, ошибке или отмене. Внутри одного каталога запускаются только соседние обычные файлы партиями до двух; каждая партия полностью завершается до обхода следующего каталога, спецфайла или обработки ошибки. Вложенные каталоги посещаются последовательно. Режим с сохранением содержимого остаётся последовательным и сохраняет прежний snapshot shape, base64, порядок детей, directory merge hash и mutation fingerprint.
- **Контракты:** экспортированные типы и функции не меняются. По умолчанию `retainContent` равно `true` и сохраняет legacy-поведение. При `false` файловые байты не собираются в один буфер: read chunk не превышает 64 КиБ; XML-проба может временно сохранить ещё до 64 КиБ префикса, то есть суммарно не более 128 КиБ на активный файл независимо от его размера. Это даёт консервативную верхнюю оценку до 32 активных файловых буферов / 4 МиБ при внешнем fan-out до 16 snapshots; XML-префиксы включены в эту оценку. Хеш сырого файла, в том числе пустого, совпадает с SHA-256 исходных байтов. XML-проба использует ровно первые 64 КиБ, собирая префикс через короткие чтения. Начатая партия дренируется до возврата или выброса; при нескольких сбоях выбирается первая ошибка в порядке входных путей, а запрошенная отмена сообщается после drain. Ошибки symlink и special entries остаются fail-closed. Нет общего кэша, пропуска source reads или изменения `pairedBSL`.
- **Приёмка:** targeted suite запрещает `readFile` на hash-only пути, проверяет совпадение raw SHA-256 и пустого файла, потоковые чтения файла больше двух блоков, split UTF-8/XML-префикс через короткие чтения, точную legacy base64 при сохранении содержимого, максимальную пару одновременных соседних файлов и последовательность рекурсии, drain/close при ошибке или отмене и воспроизводимый выбор ошибки. Синтетическая проверка фиксирует число байтов, размер блока и concurrency; она не заявляет ускорение реального сравнения без отдельного профиля.

Проверка реализации: production compile, строгий ESLint и LOC guard прошли; целевой runner завершил 17 suites с результатом 246/246 и удалил собственное дерево сборки. Внутри них проверены 19 сценариев captured write/snapshot и 19 сценариев валидации расширений. Реальный headless Edge повторил preview/approve/execute с сохранением обоих реквизитов, конфликтующей логики приёмника и неизменного источника. Ускорение полного сравнения больших конфигураций этим прогоном не измерялось.
